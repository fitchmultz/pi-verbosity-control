v5.1.2](strict-oxlint-oxfmt-5.1.2.md). The record below states what is installed, what runs, and what
the current state is. Decisions that depart from the standard's own values are recorded in
[quality-exceptions.md](quality-exceptions.md).

## Configuration and acceptance paths

- Lint configuration: `.oxlintrc.json` — the standard's baseline plus the single recorded allowance
  (QX-001) in the test-profile override. The acceptance lint command skips `tests/probes/**`; the
  qualification harness is what enforces those diagnostic fixtures.
- Formatter configuration: `.oxfmtrc.json` — the standard's formatter block with the one recorded
  formatting mapping (QX-003: the preserved four-space repository indentation).
- Acceptance entry points: `npm run check` and `npm run check:compat`, both implemented by
  `scripts/run-gates.ts`. Gates run independently — every one runs and every failure counts — and
  the aggregate exit status reports them all. Individual gates: `policy:check`, `format:check`,
  `lint`, `lint:agent`, `lint:fix`, `format`, `typecheck`, `test`, `quality:probes`, `pack:check`.

## Compiler projects and source profiles

- One TypeScript project (`tsconfig.json`) includes `**/*.ts`, so every maintained TypeScript
  source — including `tests/probes/` fixtures — is compiled under the standard's full strict option
  set. No maintained JavaScript exists; the policy verifier requires `allowJs`/`checkJs` the moment
  any appears.
- Source profiles follow `scripts/policy-baseline.ts`: production sources are `index.ts` and
  `scripts/**/*.ts`; test sources are `index.test.ts` and `tests/**/*.ts`. A source file matching
  no profile fails `policy:check`, so new maintained files must be classified deliberately.
- No handwritten declarations (`.d.ts`) are maintained, so `skipLibCheck: true` skips no
  repository-owned declarations; declaration-consumer checking is exercised by the qualification
  harness's generated declaration control.
- Test doubles follow the runtime-checked-claim pattern: the API spy is annotated with the
  extension's consumed `Pick<ExtensionAPI, ...>` surface, and recorded callables and contexts are
  narrowed through predicates rather than casts. The double provides exactly the members the
  extension's handlers read.
- Published content: `index.ts`, `README.md`, `CHANGELOG.md` (see `package.json` `files`); scripts,
  tests, and configuration are development-only.

## Formatter and generator ownership

- oxfmt owns every supported file it is pointed at, including Markdown and JSON configuration;
  formatting is expected to be idempotent, and `format:check` plus the harness's convergence
  control prove it.
- `package-lock.json` is generated by npm and skipped by oxfmt natively; npm owns those bytes and
  `npm ci` is the freshness check.
- `CHANGELOG.md` is written by the release automation (version sections, markers, and
  GitHub-generated notes) and that generator owns the file's formatting: `.oxfmtrc.json` records it
  in `ignorePatterns`. The automation's inserts vary with each release, so oxfmt ownership would
  fail `format:check` on main after a release and stall the pipeline. The historical sections are
  the same generator's past output. `package.json` is maintained and edited by the automation with
  byte-preserving slicing and `npm version`; it stays oxfmt-clean at the adopted settings.
- No code generators produce maintained sources. Files under `tests/probes/generated/` and
  `tests/probes/gate-controls/` are runtime scratch space created and removed by the harness.
